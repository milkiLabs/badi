# Building and releasing

Notes for producing a release build of this app and packaging it for Arch
Linux.

## What this is

A Flutter (Dart/UI) front end over a Zig core reached through `dart:ffi`.

The two halves are built separately and joined at bundle-install time, which is
what makes the build order matter (see [Build order](#build-order)).

## Prerequisites

Arch:

```sh
sudo pacman -S --needed flutter-bin zig cmake ninja pkgconf gtk3 gtk-layer-shell
```

`gtk-layer-shell` is not optional. The UI is a `wlr-layer-shell` surface, so
the app will not start without it, and `linux/CMakeLists.txt` fails the CMake
configure without its `.pc` file.

Verified against Flutter 3.49.0-0.2.pre and Zig 0.17.0.

## Build order

The Badi native library must exist **before** `flutter build linux`:

1. `linux/CMakeLists.txt` copies `badi_lib/zig-out/lib/libbadi.so` into the
   bundle's `lib/` at _install_ time — that is, while `flutter build` is running.
2. When the file is absent, that copy degrades to a `message(WARNING)`. The
   build still reports success, and you get a package with no FFI library that
   fails at runtime.

So: build the native library first, always.

## Shell mode (bar + on-demand launcher)

One binary, three roles:

```sh
badi            # autostart: top bar always visible, launcher hidden, serves IPC
badi --launcher # keybinding: opens the launcher via the running daemon
find / | badi   # dmenu style: lines stream to the daemon, the pick is printed
```

Bare `badi` with no daemon listening falls back to a one-shot window with
the old exit semantics, so piping keeps working without the shell running.
`Esc` closes the launcher; there is no toggle command by design.

Protocol: newline-delimited JSON over `$XDG_RUNTIME_DIR/badi.sock`
(`lib/platform/ipc.dart`). The client stays pure `dart:io` — no Flutter
init — so keypresses answer fast. A lines-mode client blocks until the
pick (stdout, exit 0) or abort (exit 1, rofi-style); an apps-mode client
exits on `ack` and the daemon owns spawning. A second open while the
launcher is visible gets an `error` reply (exit 1); close with `Esc` first.

Startup — either the user unit or a compositor `exec-once`:

```sh
systemctl --user enable --now badi   # badi --shell under graphical-session.target
```

```ini
# Hyprland
exec-once = badi --shell
bind = SUPER, SPACE, exec, badi
# Sway / Niri equivalents: exec … / spawn-at-startup …
```

State lives in `lib/shell/shell_controller.dart` (open/close/mode, no
sockets, unit-tested); completion in `lib/shell/shell_actions.dart`
(spawn-and-hide, answer-the-client). Zig reads piped stdin and batches lines;
Flutter keeps search and session interaction, with row filtering and data in
the UI-agnostic Zig core.

## Daily builds

Debug:

```sh
./tool/build_zig.sh --host
flutter run
```

Release bundle, no packaging:

```sh
cd badi_lib && zig build -Doptimize=fast && cd ..
flutter build linux --release
```

Output lands in `build/linux/x64/release/bundle/`.

> `tool/build_zig.sh` does **not** forward `-Doptimize`; it hardcodes a plain

Run the result with `./build/linux/x64/release/bundle/badi` from that
directory — the executable resolves its libraries relative to its own path.

## Regenerating bindings

`lib/core/zig.g.dart` is generated from `badi_lib/src/badi.h`, which is the source
of truth for the ABI. After changing an exported function:

```sh
dart run tool/ffigen.dart
```

This is a no-op if the header has not changed. Keep the header and the Zig
`export fn` signatures in sync by hand; nothing enforces it at compile time.

### Verifying the ABI still matches

Dart resolves symbols lazily at call time, so a stale binding fails at runtime,
not at build time. Check the contract explicitly after any FFI change:

```sh
nm -D --defined-only badi_lib/zig-out/lib/libbadi.so | grep ' T ' | awk '{print $3}' | grep '^badi_' | sort > /tmp/so.txt
grep -oE "'(badi_[a-z_]+)'" lib/core/zig.g.dart | tr -d "'" | sort -u > /tmp/dart.txt
diff /tmp/so.txt /tmp/dart.txt && echo "ABI OK"
```

An empty diff means every symbol Dart binds is exported by the library. A
symbol present in `/tmp/dart.txt` but missing from the `.so` is a hard error.

Native core:

```sh

```

Covers `apps.zig`, `icons.zig`, `parse.zig`, `exec.zig`, `session.zig`, and
`ffi.zig`. Dart widget/unit tests live in `test/`:


## Packaging for Arch

```sh
cd packaging
makepkg -sfc          # build -> badi-<ver>-<rel>-x86_64.pkg.tar.zst
makepkg -si      # build, then install
# or, for an already-built package:
sudo pacman -U badi-0.1.0-1-x86_64.pkg.tar.zst
```

`-s` is `--syncdeps` (installs missing dependencies with `pacman`); it has
nothing to do with the Dart bindings. Bindings are only regenerated by running
`dart run tool/ffigen.dart` yourself. `-f` forces the rebuild, which is what
you want after changing native code. The build performs a full
`flutter build`, so expect a few minutes.

### Installed layout

```
/usr/bin/badi              -> symlink to /usr/lib/badi/badi
/usr/lib/badi/badi
/usr/lib/badi/lib/         libapp.so, libflutter_linux_gtk.so, libbadi.so
/usr/lib/badi/data/        icudtl.dat, flutter_assets/
/usr/share/applications/badi.desktop
/usr/share/icons/hicolor/scalable/apps/badi.svg
```

**The bundle layout is load-bearing — do not flatten it.** Two independent
mechanisms depend on it:

- the executable is linked with `RUNPATH=$ORIGIN/lib`, and
- `lib/platform/zig.dart` locates `libbadi.so` relative to
  `Platform.resolvedExecutable`, which **resolves symlinks**.

Copying just the binary to `/usr/bin` leaves both pointing at directories that
do not exist, and the app fails to start. The whole bundle has to stay together
under `/usr/lib/badi` with `/usr/bin/badi` as a symlink into it.

The package also `chmod 755`s the `.so` files, which Flutter's CMake install
leaves at `0644`.

### Bumping a release

`pkgver` tracks the app version in `pubspec.yaml` (`0.1.0`). After bumping
that:

```sh
sudo pacman -S --needed devtools   # provides bumppkg
cd packaging && bump -r             # pkgrel+1 in PKGBUILD
makepkg -sfc
```

### `PKGBUILD` notes

Two things in `packaging/PKGBUILD` look odd but are deliberate:

- **`_project_root()` is a function, not a variable.** `$srcdir` is unset while
  a PKGBUILD is sourced at its top level, and makepkg sets it to
  `packaging/src`, so the project root is two levels up. Computing it in a
  function body is the only point where both facts hold.
- **`options=('!strip')`.** The bundle ships prebuilt engine and native shared
  objects; stripping them buys little and is a common source of breakage.

### Before publishing to the AUR

- Replace the placeholder artwork in `packaging/icons/badi.svg`.
- Confirm `license=('MIT')` and `pkgdesc` in `packaging/PKGBUILD`. Both were
  inferred, not verified.
- Commit the working tree first. The AUR builds from a clean checkout, so any
  uncommitted change is simply absent from the package.
- Add `packaging/*.pkg.tar.zst` and `packaging/src/` to `.gitignore`.

## Troubleshooting

### `Failed to start Flutter engine: Failed to create AOT data`

The AOT snapshot (`libapp.so`) was missing or truncated at launch time. In
practice this means a build was running concurrently and `build/` was cleared
underneath the process. Rebuild and relaunch.

Do not run `flutter build` or `rm -rf build` while the app is running from the
bundle directory.

### `file INSTALL cannot find .../build/native_assets/linux`

The Flutter tool only creates `build/native_assets/linux/` when some dependency
actually ships native assets. This project has none, so `linux/CMakeLists.txt`
now guards that install with an `EXISTS` check. If you reintroduce an
unconditional `install(DIRECTORY ...)` there, builds become intermittently
fatal.

### `libbadi.so` missing at runtime

Either the native library was never built, or it was built after `flutter build`.
Rebuild the native library first, then rebuild the bundle. See [Build order](#build-order).

### `gtk_wayland_init_if_needed: assertion 'GDK_IS_WAYLAND_DISPLAY' failed`

The app was launched outside a Wayland session. Harmless during development and
in CI; run it from a real desktop session.

### `package:layer_shell has uses-material-design: true ...`

Printed by every build. It comes from the `layer_shell` plugin, not from this
project, and does not affect the build result.
